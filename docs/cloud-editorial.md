# クラウド教科書の編集方針

## 目的
学習問題は知識を発見する入力。問題解説を時系列に並べず、前提→一般概念→製品→設計判断の順で既存の教科書へ統合する。入口は高校生、出口は実務。大学生の「ハル」がスポーツ大会サービスを起業する短い事例を共通の背景にする。スポーツ比喩は限界を述べ、正確な仕組みに戻る。

## リポジトリ調査（2026-09-19）
- 静的HTML / CSS / ブラウザJavaScript。フレームワーク、Tailwind、パッケージ管理は未使用。
- ルートはホーム、it/・math/・physics/に分野別ページ。ITはit/it.cssの暗色、青・緑のアクセント、カードを共有。880px/640pxのレスポンシブ規則がある。
- 従来のit/cloud.htmlは短い概要。本文とナビはHTMLに直書き。ネットワーク教材、クイズ、数学の静的生成スクリプトが既存資産。
- クラウド部分だけを拡張し、共通CSSや他分野を大規模に変更しない。入口URL it/cloud.htmlを維持する。

## 拡張方法
- content/cloud/topics/*.json: 1概念1ファイル。安定したid、level、order、前提、関連、本文、出典、確認日を持つ。
- content/cloud/catalog.json: 章の順序・名称。content/cloud/scenarios.json: 選択式の設計教材。
- tools/build-cloud.mjs: 依存ライブラリなし。リポジトリの位置からパスを解決し、静的HTMLと検索用データを生成する。生成HTMLは直接編集しない。
- it/cloud/: 概念ごとの恒久URL。章内順序を変えてもURLを維持する。削除・改名時は旧リンクを維持する。
- 本文はJavaScript無効でも読める。検索・既読・サクセスモードだけ段階的に追加。個人の読書進捗は端末内保存でGitHubには送らない。

## 問題を受け取ったときの手順
1. 中心テーマ、問われる知識、前提知識、周辺知識、比較技術、誤答が狙う誤解、実務用途を分析する。
2. 既存トピックを検索し、統合先、新章の必要性、改善すべき説明、追加する関連リンクを決める。
3. 問題文を転載せず、元問題なしで読める本文へ書き直す。新概念のみ新ファイルにする。前提は読む順番より前に置く。
4. 必要性→比喩と限界→仕組み→構成内の位置→具体例→比較→長短→実務判断→誤解→要点を説明する。初出の用語を説明する。
5. 製品仕様は公式資料で確認し、該当トピックのsourcesとverifiedを更新する。一般概念と製品固有仕様を分ける。3社比較は同等機能を保証しない。
6. docs/cloud-learning-log.mdに学び・統合先・改善内容を残す。問題や選択肢、個人情報は保存しない。
7. node tools/build-cloud.mjs、node tools/check-cloud.mjsで生成・リンク・前提・整合性を検証する。UI変更はブラウザで表示と操作を確認する。
8. 意味のある単位でコミットしGitHubへpush。変更と検証結果をPRに記録する。公開ブランチの反映はその時のユーザー指示に従う。

## 図解を中心に説明する（2026-09-20追加）
- ユーザーの希望：ピラミッド、フローなど多様な図を積極的に使い、可視化して理解を助ける。
- 前提や積み上がりは階層・ピラミッド、処理はフロー、選択条件は分岐、配置と接続は構成図、通信は順序図、復旧は時間軸、責任や機能は比較図で表す。装飾のために種類を増やさない。
- 図には「何を読む図か」「矢印・色・幅の意味」「省略や比喩の限界」を添える。色だけに意味を頼らずラベルを付ける。
- 原則は編集可能なHTML/CSS/SVG。図の編集元は `content/cloud/diagrams.json`、描画は `tools/cloud-diagrams.mjs`。本文の深掘り節は各topicの任意の `deepDive` 配列で管理する。
- 狭い画面で文字を極端に縮小しない。必要な図だけ領域内で横スクロールできるようにし、読み方の文章も用意する。
- 新しい問題を統合する際は、誤解を解く図や既存図の更新が必要かを毎回検討する。図と本文の内容を同時に整合させる。

## サクセスモードの編集
教科書を優先する。会社の選択で負荷・データ・目標が変わる。選択肢は唯一正解にせず、結果・理由・利点・弱点・比較・判断基準を提示する。実測でない数値や費用を実測のように見せない。
